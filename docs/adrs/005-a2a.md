# ADR-005: A2A support — a2a-sdk 1.x, generated Agent Cards, external agents

## Status

Accepted

## Date

2026-08-31

## Owners

Open Simple Agent maintainers

## Context

P2.1 requires Agent-to-Agent (A2A) interoperability: managed agents must be
exposable as A2A servers (Agent Cards, task-based invocation), and OSA must
track *external* A2A agents as configuration records distinct from managed
agents. Google ADK itself depends on `a2a-sdk` (its `a2a` extra pins
`a2a-sdk[http-server]>=0.3.4,<2`), and the 1.x line of that SDK is the
current, protobuf-typed major.

## Decision drivers

- One protocol/SDK surface shared with google-adk (version-conflict safety).
- Managed agents must be reachable as A2A servers without new process types:
  the existing runtime API gains A2A routes.
- External agents are configuration, not deployments: OSA must never deploy
  them.
- Authentication/authorization must use the shared P2.2 boundary; A2A
  security-scheme metadata and enforcement must not drift from HTTP routes.

## Considered options

1. **`a2a-sdk` 1.x (protobuf types, current major)** — what installs today;
   ADK's range permits it; FastAPI/Starlette route builders included.
2. **a2a-sdk 0.3.x (pydantic types)** — older major; would force a pin that
   fights ADK's `<2` ceiling over time.
3. **Hand-rolled JSON-RPC task protocol** — full control, unacceptable
   maintenance and compatibility cost.

## Decision

- Pin **`a2a-sdk[http-server]>=1.0,<2`** as the optional
  `osa-adk-runtime[a2a]` extra (the 1.x line, protobuf-typed protocol
  messages). Within the major, the SDK owns protocol evolution; crossing the
  major requires an ADR revision.
- **Agent Cards** are generated from validated `AgentDefinition`s plus
  resolved skills (`build_agent_card`): name/version/description from
  metadata, skills from the Skill Catalog, streaming disabled, and the
  service URL supplied by deployment/runtime configuration. The runtime API
  serves the card at the A2A well-known path.
- **A2A server semantics**: the runtime exposes A2A JSON-RPC routes backed
  by an `AgentExecutor` that maps `message/send` to `GenericAdkAgent.invoke`
  — one A2A task per invocation, completed with the agent's output text as
  an artifact; errors map to task failure states and SDK cancellation maps to
  one canceled terminal state. Sessions: the A2A context id is used as the
  OSA session id so multi-turn conversations work through the normal session
  ownership model (anonymous user unless propagated).
- **External agents** are a distinct Control Plane record type
  (`ExternalAgentRecord`: URL, cached Agent Card, health/last-checked) with
  their own catalog and API. Registration fetches and validates the remote
  Agent Card; **external records can never be deployed** — the deploy path
  rejects them structurally.
- **Remote invocation** is exposed to managed agents as a native tool
  (`RemoteA2aTool`) constructed from an external-agent record: the model can
  call the remote agent through the A2A client with bounded timeouts and
  deterministic error mapping (`a2a_remote_failed`).
- **Security schemes**: `A2AConfig` remains the agent-level switch
  (`a2a.enabled`); OIDC/OAuth configuration is externalized through
  `OSA_AUTH_*`. Protected Agent Cards advertise the required `osa_oidc`
  bearer/OIDC scheme, and the shared middleware enforces authentication and
  route permissions on inbound JSON-RPC requests. Validated subject and tenant
  claims propagate into the OSA invocation. Outbound external-agent records
  may use the shared API-key, OAuth2 client-credentials, or mTLS adapter;
  secret values are resolved per call and never persisted. No anonymous
  external invocation endpoints beyond what the configured auth mode allows.
- **Task persistence**: A2A uses the SDK's `DatabaseTaskStore` when
  `OSA_A2A_TASK_DATABASE_URL` is configured, with a bounded operator-selected
  table name (`OSA_A2A_TASK_TABLE`, default `osa_a2a_tasks`) and an OSA owner
  resolver that combines tenant and subject. Without the DSN, the existing
  `InMemoryTaskStore` remains the development default. The runtime initializes
  the configured store before readiness and disposes its SQLAlchemy engine on
  shutdown. PostgreSQL is the shared-production choice; SQLite is supported
  only as an explicit local option where the SDK permits it. The explicit
  `osa-a2a-migrate` command provisions the SDK task table, a version row, and
  the OSA `<task_table>_ownership` table; runtime startup validates rather than
  mutates that schema. Ownership rows are tenant/caller scoped and use worker
  leases, heartbeats, fencing epochs, and durable cancellation requests. The
  SDK task store is wrapped with an OSA fence-aware adapter: each task save
  carries the acquired ownership snapshot through the call context and holds
  the ownership-row lock through the database mutation.

## Consequences

### Positive

- Managed agents become A2A servers and A2A clients through one supported
  SDK, sharing google-adk's dependency range.
- The acceptance "agent A invokes agent B and a deterministic external A2A
  agent" is testable offline with in-process servers.

### Negative or trade-offs

- Protobuf-typed protocol messages (1.x) differ from a2a-sdk 0.3.x's
  pydantic models; OSA isolates the mapping in one module.
- Durable task records and OSA ownership leases can be shared across replicas
  when the PostgreSQL DSN is configured. SDK task saves are guarded by the OSA
  ownership fence and fail closed after lease loss, but the SDK active-task
  registry remains process-local.
- Local cancellation emits one terminal canceled event before the handler is
  drained. Independent handlers can look up shared active tasks; remote
  cancellation waits for the durable owner, and an expired owner can be
  replaced under a new fence and finalized without replaying agent side
  effects. Terminal snapshots are replayed through read-only SDK events. True
  multi-process handler recovery, late-event acceptance, and non-idempotent
  retry policy remain part of the P2.4 acceptance contract.

## Validation

- Offline protocol tests run a real A2A server in-process (uvicorn on
  localhost) with a scripted agent: card fetch, message/send → task
  completed, error mapping.
- The acceptance flow (agent A invoking agent B and a deterministic external
  A2A agent through the same client path) is covered by integration tests.

## Follow-up

- [x] P2.2: enforce the shared bearer/OIDC boundary on inbound A2A calls and
      propagate the authenticated subject/tenant; outbound credentials use the
      shared adapters in ADR-006.
- [x] Durable A2A task-record storage and tenant/subject ownership via the
      pinned SDK `DatabaseTaskStore` (opt-in PostgreSQL).
- [x] Fence SDK task saves with the current OSA ownership epoch and stop a
      worker that loses its lease without publishing a synthetic failure.
- [x] P2.4 cancellation slice: independent-handler lookup, remote cancellation
      waiting, expired-owner cancellation takeover, and read-only terminal
      replay are covered by focused SQLite acceptance; fenced SDK saves and the
      PostgreSQL task-store/ownership replica acceptance remain in place.
- [ ] P2.4 remaining: add true multi-process/multi-worker PostgreSQL handler
      acceptance for active-task recovery, streaming, late events, and decide
      the non-idempotent owner-loss/retry policy.
